# Voice Anti-Spoofing: LCNN на ASVspoof2019 LA

Система детекции синтезированной и преобразованной речи (countermeasure, CM) на
логическом доступе (Logical Access) датасета
[ASVspoof2019](https://datashare.ed.ac.uk/handle/10283/3336).
Модель: Light CNN ([arXiv:1511.02683](https://arxiv.org/abs/1511.02683),
[arXiv:1904.05576](https://arxiv.org/abs/1904.05576)), рецепт обучения взят из
[arXiv:2103.11326](https://arxiv.org/abs/2103.11326).

**Итог: EER 3,0704 % на полной eval-партиции (71 237 записей), оценка 10 / 10 по
официальному `grading.py`.** Результат даёт фьюжн пяти наборов скоров: четыре
чекпоинта LFCC-модели и один чекпоинт модели на спектрограмме. Разбор чисел в
разделе [Результаты](#результаты), точные команды в разделе
[Воспроизведение результата](#воспроизведение-результата).

Логи обучения опубликованы:
[comet.com/a-ern/asvspoof-lcnn](https://www.comet.com/a-ern/asvspoof-lcnn).

Проект построен на
[PyTorch Project Template](https://github.com/Blinorot/pytorch_project_template):
конфигурация через [Hydra](https://hydra.cc/), логирование экспериментов через
[Comet ML](https://www.comet.com/docs/v2/).

## Задача и метрика

Требуется бинарно классифицировать запись: `bonafide` (настоящая речь человека)
или `spoof` (запись, синтезированная TTS или полученная voice conversion).
Партиция LA содержит 19 алгоритмов атак, причём атаки в `eval` (A07-A19) не
пересекаются с атаками в `train`/`dev` (A01-A06), поэтому модель обязана
обобщаться на не виденные типы спуфинга.

| Партиция | Записей | bonafide | spoof  |
| -------- | ------- | -------- | ------ |
| train    | 25 380  | 2 580    | 22 800 |
| dev      | 24 844  | 2 548    | 22 296 |
| eval     | 71 237  | 7 355    | 63 882 |

Основная метрика здесь **EER** (Equal Error Rate): порог, при котором доля
ложных отклонений bonafide равна доле принятых spoof. Скором системы служит
логарифмическое отношение правдоподобий `logits[:, 1] - logits[:, 0]` (чем
больше, тем вероятнее bonafide). Реализация EER в `src/metrics/eer_utils.py`
совпадает с официальным `calculate_eer.py` курса, поэтому локальные числа
сравнимы с числами грейдера.

EER не раскладывается по батчам: среднее по-батчевых EER не равно EER корпуса.
Поэтому тренер накапливает скоры всей валидационной партиции и считает метрику
один раз за эпоху. Она логируется как `dev_EER`, и по ней выбирается лучший
чекпоинт.

## Архитектура решения

**Front-end.** Два варианта, оба участвуют в итоговом результате.

| Front-end | Конфиг | Вход модели | Параметров |
| --------- | ------ | ----------- | ---------- |
| логарифмическая STFT-спектрограмма (окно Блэкмана, `n_fft = 1724`, `hop = 130`) | `-cn=lcnn` | 863 × 600 | 10 198 818 |
| LFCC (20 коэффициентов + Δ + ΔΔ, окно 20 мс, шаг 10 мс) | `-cn=lcnn_lfcc` | 60 × 750 | 865 058 |

Разница в размере целиком приходится на первый полносвязный слой: голова LCNN
разворачивает всю карту признаков в вектор, поэтому число параметров зависит от
разрешения входа. При этом главный вклад в итоговый EER даёт как раз меньшая
LFCC-модель, а не десятимиллионная на спектрограмме.

Все записи приводятся к **77 870 отсчётам (4,87 с при 16 кГц)**: случайная
обрезка на обучении, циклический повтор сигнала при паддинге (тишина в конце
записи не несёт признаков спуфинга и работает как ложная подсказка). Признаки
считаются батчем на GPU (`batch_transforms`), а не в даталоадере, иначе
front-end упирается в CPU.

**Модель.** LCNN: 9 свёрточных слоёв с активацией Max-Feature-Map (MFM берёт
поэлементный максимум двух половин карт признаков, то есть учит фильтр
конкурировать сам с собой и работает как обучаемый ReLU), 4 max-pooling слоя,
батч-нормализации, затем dropout `0.75` перед финальным полносвязным слоем;
порядок «сначала dropout, потом BatchNorm» взят из статьи STC.

**Обучение.** Adam, `lr = 3e-4`, `weight_decay = 1e-4`, StepLR с уменьшением
lr вдвое каждые 10 эпох. Cross-Entropy с весами классов `[1.0, 8.84]`,
компенсирующими дисбаланс train (22 800 spoof против 2 580 bonafide).
Обучение идёт в bfloat16 (`torch.autocast`): вход `863 × 600` делает активации
основным потребителем памяти, а bf16 сохраняет диапазон fp32, поэтому
`GradScaler` не нужен.

### Настройка трекера экспериментов

Логи пишутся в [Comet ML](https://www.comet.com/). Нужен API-ключ: либо
переменная окружения, либо файл `~/.comet.config`, который создаётся при первом
`comet login` и подхватывается автоматически.

```bash
export COMET_API_KEY=<ваш ключ>
# либо ~/.comet.config:
# [comet]
# api_key = <ваш ключ>
```

Workspace берётся из того же файла; при работе в команде его можно задать явно
через `writer.workspace=<workspace>`. Проект по умолчанию называется
`asvspoof-lcnn`; логи запусков этого репозитория лежат в
[comet.com/a-ern/asvspoof-lcnn](https://www.comet.com/a-ern/asvspoof-lcnn).

Без интернета запускайте с `writer.mode=offline`: эксперимент сложится в
`.cometml-runs/<id>.zip` рядом с запуском и загрузится позже командой
`comet upload <файл>.zip`. Если вместо Comet нужен WandB, добавьте к запуску
`writer=wandb` (потребуется `wandb login`).

## Данные

Скачайте архив LA (≈7.6 ГБ) и распакуйте:

```bash
curl -L -o LA.zip "https://datashare.ed.ac.uk/bitstreams/a9f87c35-f055-4015-80e2-2fdff0d46269/download"
unzip LA.zip -d data/
```

Ожидаемая структура (`data_dir` указывает на каталог, содержащий эти папки):

```
LA/
├── ASVspoof2019_LA_train/flac/
├── ASVspoof2019_LA_dev/flac/
├── ASVspoof2019_LA_eval/flac/
└── ASVspoof2019_LA_cm_protocols/
    ├── ASVspoof2019.LA.cm.train.trn.txt
    ├── ASVspoof2019.LA.cm.dev.trl.txt
    └── ASVspoof2019.LA.cm.eval.trl.txt
```

Нужны **две** переменные окружения. Первая указывает на аудио, вторая на
eval-протокол, по которому проверяется полнота сабмита:

```bash
export ASVSPOOF_DIR=/path/to/LA/LA
export ASVSPOOF_EVAL_PROTOCOL=$ASVSPOOF_DIR/ASVspoof2019_LA_cm_protocols/ASVspoof2019.LA.cm.eval.trl.txt
```

Задать только первую недостаточно: путь к протоколу берётся не из `ASVSPOOF_DIR`,
а отдельно, и без второй переменной проверка покрытия протокола ищет файл в
`data/LA/` внутри репозитория и падает. Значения по умолчанию (когда обе
переменные не заданы) рассчитаны на распакованный корпус в `data/LA/`.

Индекс партиции строится по протоколу один раз и кэшируется в `data/index/`.

## Обучение

Сначала sanity-check на 64 фиксированных записях: пайплайн исправен, если лосс
уходит почти в ноль, а EER на тех же данных обращается в ноль.

```bash
python3 train.py -cn=one_batch
```

### Команды, которыми получен итоговый результат

Модель на спектрограмме (прогон `lcnn_stft_600f`):

```bash
python3 train.py -cn=lcnn writer.run_name=lcnn_stft_600f trainer.seed=1 \
    trainer.cudnn_benchmark=True dataloader.batch_size=32 \
    dataloader.num_workers=6 trainer.n_epochs=30
```

Модель на LFCC (прогон `lcnn_lfcc_seed1`):

```bash
python3 train.py -cn=lcnn_lfcc writer.run_name=lcnn_lfcc_seed1 trainer.seed=1 \
    trainer.cudnn_benchmark=True dataloader.batch_size=32 \
    dataloader.num_workers=5 trainer.n_epochs=30 trainer.save_period=3
```

`trainer.save_period=3` во второй команде обязателен. По умолчанию он равен 5, и
тогда чекпоинтов эпох 12, 18 и 21 не существует вовсе, а итоговый результат
собран именно из них.

Любой параметр переопределяется из командной строки:

```bash
python3 train.py -cn=lcnn dataloader.batch_size=16 trainer.n_epochs=50 \
    writer.run_name=lcnn_bs16 trainer.override=True
```

Полезные ключи `trainer`:

| Ключ            | Значение                                                       |
| --------------- | -------------------------------------------------------------- |
| `use_amp`       | обучение в bf16 (по умолчанию `True`)                           |
| `override`      | перезаписать каталог `saved/${writer.run_name}`                 |
| `resume_from`   | продолжить обучение с чекпоинта внутри каталога запуска         |
| `from_pretrained` | инициализировать веса из произвольного `.pth`                 |
| `monitor`       | метрика для лучшего чекпоинта, по умолчанию `min dev_EER`       |
| `save_period`   | как часто сохранять промежуточный чекпоинт, по умолчанию 5 эпох |
| `early_stop`    | сколько эпох без улучшения ждать до остановки                   |
| `cudnn_benchmark` | автоподбор алгоритмов свёрток, по умолчанию `False`           |

Про `cudnn_benchmark` отдельно: размер входа здесь фиксирован (863×600), поэтому
автоподбор алгоритмов cuDNN окупается: замер даёт ускорение в 2.1 раза
(с 70 до 145 утт/с). Платить приходится воспроизводимостью: алгоритм выбирается
по замерам времени и может отличаться от запуска к запуску. **Оба финальных
прогона шли с `cudnn_benchmark=True`, поэтому побитово они не повторяются**: при
том же `trainer.seed=1` повторный запуск даст близкие, но не идентичные веса и
числа. Для точно воспроизводимого запуска оставьте значение по умолчанию
`False` (`cudnn.deterministic=True`).

Тот же ключ есть у `inferencer` в `inference.yaml`.

Длина окна, до которой доводится каждая запись в батче, задаётся одним
параметром `collate_max_len` (77 870 отсчётов, 4,87 с при 16 кГц): на него
ссылается и `max_len` датасетов (обрезка при чтении файла), и `collate_fn`.
Меняя его, не забудьте про `model.in_frames`.

Чекпоинты и конфиг запуска пишутся в `saved/${writer.run_name}/`, лучший из них
`model_best.pth`. В Comet ML логируются лосс на train/dev, `dev_EER`, learning
rate, норма градиента и гистограммы скоров отдельно для bonafide и spoof: их
расхождение наглядно показывает, насколько классы разделимы.

## Инференс и сабмит

Инференс на eval-партиции с лучшим чекпоинтом:

```bash
python3 inference.py inferencer.from_pretrained=saved/lcnn_stft_600f/model_best.pth
```

Результат сохраняется в `data/saved/eval/`:

- `eval_scores.csv` в сабмит-формате: без заголовка, `utterance_id,score`;
- `eval_outputs.pth` с логитами, скорами и метками всей партиции одним файлом
  (для анализа распределений и фьюжна нескольких систем).

Если у партиции есть разметка, EER печатается сразу после инференса.

`inference.py` берёт front-end из текущих конфигов проекта, а они описывают
спектрограмму. Для LFCC-чекпоинта front-end и размеры входа надо задать явно,
иначе веса загрузятся к чужому front-end:

```bash
python3 inference.py transforms=lfcc model.in_freq=60 model.in_frames=750 \
    inferencer.from_pretrained=saved/lcnn_lfcc_seed1/model_best.pth
```

`scripts/predict_eval.py` из следующего раздела делает это сам, восстанавливая
входной тракт по конфигу рядом с чекпоинтом.

Перед отправкой файл проверяется скриптом: он ловит всё, на чём падает или
занижает оценку официальный `grading.py` (пропущенные utterance_id, дубликаты,
NaN, лишние колонки), печатает EER и ожидаемую оценку, после чего копирует
результат под нужным именем:

```bash
python3 scripts/make_submission.py data/saved/eval/eval_scores.csv
```

```
protocol: 71237 trials from .../ASVspoof2019.LA.cm.eval.trl.txt
scores:   71237 unique ids from mppanin.csv

bonafide trials: 7355, spoof trials: 63882
EER: 3.0704%
expected performance grade: 10.00 / 10
```

Путь к протоколу задаётся флагом `-p` или переменной `ASVSPOOF_EVAL_PROTOCOL`,
а имя выходного файла флагом `-o`.

## Воспроизведение результата

### Одна команда на один чекпоинт

`scripts/predict_eval.py` делает всё, что нужно для сдачи: прогоняет чекпоинт по
всей eval-партиции, проверяет, что предсказана каждая запись протокола, пишет
сабмит и печатает EER с ожидаемой оценкой.

```bash
python3 scripts/predict_eval.py saved/lcnn_lfcc_seed1/model_best.pth -o mppanin.csv
```

Главное отличие от `inference.py`: параметры входного тракта берутся из
`saved/<run_name>/config.yaml`, лежащего рядом с чекпоинтом, а не из текущих
конфигов проекта. Это не перестраховка: `load_state_dict` сверяет только формы
весов, поэтому чужая длина окна или чужой размер БПФ загружаются молча, а замер
на обученной модели показал, что один только посторонний `collate_max_len`
сдвигает eval EER на 0.33 пункта и переворачивает знак скора у части записей.

Для LFCC-чекпоинта скрипт печатает список расхождений с конфигами проекта
(`inference.yaml` описывает спектрограмму) и сообщение о том, что используется
конфигурация из чекпоинта. Это штатный вывод, а не предупреждение: front-end
восстановлен по обучающему прогону.

Сабмит записывается только после проверки покрытия протокола: файл с дырой это
`KeyError` в грейдере и ноль за работу, поэтому лучше, чтобы такого файла на
диске вообще не было. Строки идут в порядке протокола, скоры пишутся через
`repr`, без округления: округление создаёт совпадающие скоры у записей, которые
модель развела, а совпадения сдвигают EER.

Полезные флаги:

| Флаг            | Значение                                                     |
| --------------- | ------------------------------------------------------------ |
| `-b`, `--batch-size` | размер батча, по умолчанию 32                           |
| `-d`, `--device` | `auto`, `cpu` или конкретное cuda-устройство                 |
| `-j`, `--num-workers` | воркеры даталоадера, по умолчанию 4                    |
| `--save-dir`    | куда класть сырые предсказания, по умолчанию `data/saved/eval` |
| `--limit`       | прогнать первые N записей для быстрой проверки пайплайна      |
| `-p`, `--protocol` | протокол, по которому проверяется полнота                  |

### Итоговый файл целиком

Пять прогонов и фьюжн. Команда проверена и даёт побайтово тот же `mppanin.csv`:

```bash
for e in 12 15 18 21; do
  python3 scripts/predict_eval.py saved/lcnn_lfcc_seed1/checkpoint-epoch$e.pth \
      --save-dir data/saved/lfcc$e -o data/saved/lfcc$e.csv
done
python3 scripts/predict_eval.py saved/lcnn_stft_600f/checkpoint-epoch15.pth \
    --save-dir data/saved/stft15 -o data/saved/stft15.csv
python3 scripts/fuse_scores.py \
    data/saved/{lfcc12,lfcc15,lfcc18,lfcc21,stft15}/eval_scores.csv -o mppanin.csv
```

**`--save-dir` здесь обязателен.** По умолчанию все прогоны пишут сырые
предсказания в один и тот же каталог `data/saved/eval/`, то есть каждый
следующий чекпоинт затирает `eval_scores.csv` предыдущего, и на вход фьюжну
уходят пять копий последнего прогона.

### Фьюжн нескольких прогонов

Объединение скоров нескольких систем это стандартный последний шаг в этой
задаче: в [arXiv:1904.05576](https://arxiv.org/abs/1904.05576) фьюжн даёт 1.84%
EER против 4.53% у лучшей одиночной системы. Условие задания при этом не
нарушается, архитектура у всех участников одна и та же (LCNN), различаются
front-end и номер эпохи.

```bash
python3 scripts/fuse_scores.py \
    data/saved/stft15/eval_scores.csv data/saved/lfcc21/eval_scores.csv \
    -o data/saved/fused_scores.csv
```

На вход идут и сабмит-csv, и `.pth` с логитами. Скоры разных прогонов
несопоставимы по масштабу (у одного LLR лежит в пределах десятков, у другого в
пределах единиц), поэтому каждый набор нормируется перед усреднением. Способа
два: `--method rank` (ранги, приведённые к отрезку [0, 1], по умолчанию) и
`--method zscore` (вычесть среднее, поделить на стандартное отклонение). Ранги
устойчивее к выбросам: одна система с тяжёлым хвостом не утянет за собой
результат. Обе нормировки монотонны, то есть EER отдельной системы от них не
меняется. Веса задаются флагом `-w` (по умолчанию равные).

Скрипт печатает EER каждой системы и EER фьюжна, так что сразу видно, есть ли
выигрыш; если участник слабее остальных, объединение может и ухудшить
результат. Наборы записей у всех входных файлов должны совпадать, иначе скрипт
останавливается: фьюжн по пересечению даст csv с дырой. Готовый файл проверяется
той же проверкой, что и обычный сабмит.

### Быстрое сравнение чекпоинтов

Полный прогон eval занимает минуты, для сравнения чекпоинтов между собой этого
слишком много. `scripts/eval_subset.py` считает EER на подвыборке протокола и
разбивку по атакам:

```bash
python3 scripts/eval_subset.py data/saved/eval/eval_scores.csv -s subset.txt
```

В файле подвыборки перечислены utterance_id, по одному на строку; без `-s`
берутся все записи протокола, для которых есть скор. Разбивка по `attack_id`
считается так же, как в официальном evaluation plan: каждая атака проверяется
против всего пула bonafide, поэтому числа сравнимы с опубликованными. Она нужна
и для отчёта: суммарный EER этой системы почти целиком складывается из одной
атаки A17, и по одному общему числу этого не видно.

### Проверка официальным грейдером

Локальная проверка `make_submission.py` повторяет логику `grading.py`, но перед
отправкой полезно прогнать и сам грейдер курса. Он читает все csv из каталога
`students_solutions` рядом с собой и берёт протокол из своего каталога:

```bash
cd /path/to/hw          # каталог с grading.py и calculate_eer.py
mkdir -p students_solutions
cp /path/to/mppanin.csv students_solutions/
python3 grading.py
cat grades.csv
```

Имя файла должно совпадать с логином: грейдер собирает из него адрес почты.
EER и оценка в `grades.csv` обязаны совпасть с тем, что напечатал
`predict_eval.py`.

## Результаты

Все числа получены на **полной eval-партиции** (71 237 записей) той же
реализацией EER, что и у грейдера.

### Одиночные системы

| Система                              | Чекпоинт             | EER, %  |
| ------------------------------------ | -------------------- | ------- |
| LFCC (`lcnn_lfcc_seed1`)             | эпоха 12             | 4,0653  |
| LFCC (`lcnn_lfcc_seed1`)             | эпоха 15             | 4,0922  |
| LFCC (`lcnn_lfcc_seed1`)             | эпоха 18             | 4,1052  |
| LFCC (`lcnn_lfcc_seed1`)             | эпоха 21             | 3,6978  |
| LFCC (`lcnn_lfcc_seed1`)             | лучший по `dev_EER`  | 3,6678  |
| спектрограмма (`lcnn_stft_600f`)     | эпоха 15             | 5,5222  |

Чекпоинт, выбранный по валидации, оказался лучшим и на eval (3,6678 %), то есть
`dev_EER` работает как отбор, несмотря на то что атаки в dev и eval не
пересекаются. Модель на спектрограмме слабее LFCC-модели почти на два пункта,
хотя параметров в ней в 12 раз больше.

### Вклад фьюжна

| Что объединяется                        | EER, %  |
| --------------------------------------- | ------- |
| лучшая одиночная система (LFCC)         | 3,6978  |
| четыре чекпоинта LFCC                   | 3,6571  |
| LFCC + спектрограмма                    | 3,4672  |
| все пять наборов скоров                 | 3,0704  |

Разложение показывает, откуда берётся выигрыш. Объединение четырёх эпох одного
и того же прогона даёт почти ничего (3,6978 → 3,6571): чекпоинты одной модели
ошибаются на одних и тех же записях. Добавление второго front-end сдвигает
результат заметно сильнее, потому что спектрограммная и кепстральная системы
ошибаются по-разному, и слабая по отдельности система (5,5222 %) улучшает
итог. Обе идеи вместе дают 3,0704 % и оценку 10 / 10.

## Реализованные альтернативы

Помимо использованной конфигурации в репозитории реализованы варианты
классификационной головы и угловые функции потерь из
[arXiv:2103.11326](https://arxiv.org/abs/2103.11326). В итоговом результате они
не участвуют и подключаются только явным переопределением конфига.

**Головы** (`src/model/lcnn_heads.py`). Штатная голова LCNN разворачивает всю
карту признаков в вектор, из-за чего число параметров зависит от разрешения
входа. Альтернативы сворачивают время: `LCNNAttention` (attention-пулинг) и
`LCNNLSTMSum` (BLSTM-суммирование). Обе выбираются готовым конфигом:

```bash
python3 train.py -cn=lcnn model=lcnn_attention
python3 train.py -cn=lcnn model=lcnn_lstm
```

Не использованы, потому что базовая голова из таблицы 1 статьи STC уже давала
целевую оценку, а смена головы меняет модель целиком и потребовала бы повторить
весь цикл обучения обеих систем.

**Угловые функции потерь** (`src/loss/margin_losses.py`): `AMSoftmaxLoss`,
`OCSoftmaxLoss`, `P2SGradLoss`. Требуют эмбеддинга, а не логитов, поэтому
включаются вместе с `model.return_embedding=True`:

```bash
python3 train.py -cn=lcnn model.return_embedding=True \
    loss_function._target_=src.loss.P2SGradLoss \
    '~loss_function.class_weights' +loss_function.embed_dim=80
```

`embed_dim = 80` это размер эмбеддинга модели: `embedding_dim: 160` в конфиге,
пополам после MFM. Веса классов удаляются, потому что у угловых функций потерь
их нет.

Не использованы по результатам сравнительного исследования Wang и Yamagishi:
для LCNN-систем преимущество маржинальных функций потерь над взвешенной
перекрёстной энтропией не является статистически значимым и перекрывается
разбросом от случайной инициализации. Подробнее в отчёте.

## Тесты

Тесты не трогают настоящий корпус: каждый фикстур собирает во временном каталоге
синтетический LA с той же раскладкой и тем же форматом протокола, поэтому весь
набор выполняется на CPU за несколько секунд и запускается на любой машине.

```bash
python3 -m pytest tests/ -q
```

162 теста покрывают модель и оба front-end (форма выхода, размер модели,
циклический паддинг, детерминизм инференса), взвешенную функцию потерь, коллацию
батча, расчёт EER и разбивку по атакам, фьюжн скоров, проверку сабмита, сверку
конфига чекпоинта с текущим и отбор лучшего чекпоинта по монитору.

Проверки стиля те же, что в pre-commit (`isort` вызывается с профилем `black`,
иначе две утилиты спорят о переносах в многострочных импортах):

```bash
black --check . && isort --profile black --check-only . && flake8 .
```
